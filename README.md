# Student Transport Management System

A transport management application for a college transport cell. Written in
C++17 with a layered architecture and CSV persistence, and shipped with **two
front ends over one shared domain layer** — a console application and a native
Qt Widgets desktop application.

Students take a seat on a route, see exactly what they owe, pay against either
fee bucket, and track their complaints to resolution. Staff manage the roster,
routes, seats, dues, complaints and notices. An administrator oversees all of it.

## Quick start

Requires CMake 3.16+ and a C++17 compiler (GCC 9+, Clang 10+, MSVC 2019+).

### Run the desktop application

```bash
sudo apt install qt6-base-dev      # or your distro's Qt 6 package
cmake -S . -B build
cmake --build build
./build/bin/transport_gui
```

Qt 6.2+ is required (`Qt6::Widgets` and `Qt6::PrintSupport`). If Qt is absent,
CMake skips the `transport_gui` target with a note rather than failing, so the
console build still works.

First run creates `data/` and an administrator account:

| Username | Password |
| ---------- | ---------- |
| `admin` | `admin123` |

Change it immediately from **My profile**. Accounts created in either front end
are visible in the other immediately.

### Run the console application

```text
cmake -S . -B build
cmake --build build
./build/bin/transport_system
```

### Tests

```text
ctest --test-dir build --output-on-failure
```

### Editor

VS Code tasks wrap CMake (**CMake: Configure / Build / Test**, **Run desktop
GUI**); launch configurations cover both applications and every test suite.
See [Editor setup](#editor-setup-vs-code).

### Build targets

| Target | Links | Purpose |
| -------- | ------- | --------- |
| `transport_domain` | — | Models, repositories, services, utils. No console code, no Qt. |
| `transport_core` | `transport_domain` | Adds `src/ui/`, the console front end. |
| `transport_system` | `transport_core` | The console executable. |
| `transport_gui` | `transport_domain` + Qt 6 | The desktop executable. |
| `gui_capture` | `transport_domain` + Qt 6 | Optional dev tool that regenerates the screenshots in this file. |
| `test_*` (6) | `transport_core` | The 69 tests. |

`transport_gui` deliberately does **not** link `transport_core`. If it did, the
desktop application would carry `iostream` and terminal code it never uses, and
the layering that keeps the domain reusable would stop meaning anything.

### Dependency rules

1. The domain depends on nothing above it — no Qt, no console, no knowledge of
   either front end.

2. Controllers depend on the domain plus `QString` for their view structs.

3. Widgets depend on controllers. **No page includes a service header.**

4. `AppContext` is the single place that knows all the services exist, which
   keeps construction explicit and avoids a service locator spread across pages.

Why the controller layer matters: "outstanding" is computed once, in
`PaymentController`. The dashboard card, the fee summary, the roster column and
the reports financial block all read it, so they cannot drift apart. The
original project stored a single `due` field that the total re-added a
registration fee to — exactly the class of bug a shared computation prevents.

## How the two front ends fit together

```text
                 transport_domain        models, repositories, services,
                        |                utils — no console code, no Qt
            +-----------+-----------+
            |                       |
     transport_core           transport_gui
  (domain + src/ui/*.cpp)   (domain + controllers + Qt Widgets)
            |                       |
    transport_system          desktop application
  (the console app)
```

`src/ui/` is the only console-specific code in the project, so keeping it out of
`transport_domain` is what lets the desktop front end reuse the tested logic
verbatim. The 69 tests link `transport_core` and are completely unaffected by
the GUI existing.

Both front ends read and write the same CSV files, so accounts, routes, seats,
payments, complaints and notices are interchangeable between them.

## Data and persistence

Storage is plain CSV, one file per aggregate. Nothing above the repository layer
knows that, so moving to SQLite means reimplementing five classes and nothing
else.

| File | Holds | Notes |
| ------ | ------- | ------- |
| `users.csv` | students, staff, administrators | Salted, iterated password digest — never plaintext |
| `routes.csv` | routes, fares, capacity | Defaults seeded on first run |
| `payments.csv` | every payment as an immutable journal row | Balances are derived, never stored |
| `complaints.csv` | complaints, staff responses, resolution |  |
| `notices.csv` | published announcements |  |
| `config.csv` | fees, institution details, staff authorization code | Editable without recompiling |

### Writing a payment

Every money movement is appended to the journal and the running balances are
recomputed from it. This is what makes partial payment and payment history
possible; the original stored only a `paid` boolean.

```mermaid
sequenceDiagram
    actor S as Student
    participant P as PaymentsPage
    participant C as PaymentController
    participant PS as PaymentService
    participant R as CsvPaymentRepository

    S->>P: Confirm payment, ₹5,000 against Transport
    P->>C: record(studentId, Transport, 5000, recorder)
    C->>PS: recordPayment(...)
    PS->>PS: validate amount is positive
    PS->>PS: cap at this bucket's remaining balance
    PS->>R: append(Payment row)
    R-->>PS: written
    PS->>PS: AuthService.onJournalChanged()
    PS-->>C: PaymentReceipt { reference, applied, outstandingAfter }
    C-->>P: ActionResult + ReceiptView
    P->>P: re-read statement, re-render
    P-->>S: toast + refreshed balances
```

### Legacy migration

If the pre-refactor files (`list_of_students`, `login.txt`) are present they are
imported exactly once, guarded by a marker file, and every run is recorded in
`data/migration.log` so the import is auditable. Imported accounts use the
placeholder secret `legacy` and should be reset.

## Business rules

**Seat** — one student, one seat; one seat, at most one student.

```mermaid
stateDiagram-v2
    direction LR
    [*] --> Available : route created
    Available --> Selected : student clicks a free seat
    Selected --> Occupied : SeatService.assign writes the student record
    Occupied --> Available : seat released, or the student changes route
```

A second student cannot take an occupied seat: `isSeatTakenByOther` rejects the
assignment, and changing route releases the old seat and rolls back if the new
one cannot be taken.

**Payment** — registration and transport are settled independently.

```mermaid
stateDiagram-v2
    direction LR
    [*] --> AwaitingSeat : account created
    AwaitingSeat --> Pending : a seat is taken, transport fee applies
    Pending --> Partial : one bucket partly paid
    Partial --> Settled : both buckets cleared
    Partial --> Partial : payment capped at the bucket's remaining balance
```

**Complaint** — open, resolved, reopened.

```mermaid
stateDiagram-v2
    direction LR
    [*] --> Open : student submits
    Open --> Resolved : staff records a response
    Resolved --> Open : staff reopens
```

### Invariants behind those transitions

- **Seat ownership lives on the `Student` record** (`routeId` + `seatNumber`), and
  `SeatService` is the only code permitted to write it. There is deliberately no
  `SeatRepository` and no `seats.csv` — a second source of truth would make
  "one seat, one student" impossible to guarantee. Occupancy is always derived
  by asking which students hold which seat.

- **Payments are capped per bucket**, so a payment can settle registration in
  full without silently zeroing the transport balance.

- **A route cannot be deleted** while students are allotted to it, and its
  capacity cannot drop below the number already allotted.

## Features

**Students** — dashboard, profile, route selection, seat map, allotment card,
per-bucket payments with receipts, payment history, complaints with staff
responses, notice board, password change, logout.

**Staff** — dashboard, self-assignment to a route, student roster, route CRUD,
seat allocation, per-student and aggregate dues, complaint queue with
resolve/reopen, notice publish/edit/delete, reports, logout.

**Admin** — everything staff can do, plus staff account oversight.

Both front ends implement the same feature set. The console version is the
reference for keyboard-driven use; the desktop version adds search and
filtering, CSV export, printable cards, light and dark themes, and data backup
and restore.

### Theming

One stylesheet, `resources/styles/app.qss`, with `{{TOKEN}}` placeholders that
`Theme.cpp` substitutes from the active palette. Light and dark share the same
rules and **no widget hardcodes a colour**. 31 SVG icons ship in
`resources/icons/` via `resources.qrc`; nothing is fetched at runtime, so the
application works offline. The theme is persisted in `QSettings` and switchable
from the top bar or from Settings.

### Navigation

`MainWindow` owns a sidebar of checkable buttons in a `QButtonGroup` and a
`QStackedWidget` of pages; the label list is derived from the session role. One
window serves all three roles rather than three separate windows.

### Notifications

Two channels, deliberately separated: **toasts** for routine outcomes (a payment
recorded, a seat assigned) which auto-dismiss with a fade, and **modal dialogs**
for anything destructive or critical. Every destructive action goes through one
`confirm` helper that defaults to Cancel.

### Accessibility

- Tab order follows creation order; the seat grid is real buttons, so arrow keys
  and Tab both work.

- Every control has a text label. Icons are supplementary, never the only cue.

- Focus is visible; Escape closes dialogs; Enter submits login, password change
  and payment forms.

- Status is never conveyed by colour alone — every status cell also carries a
  word such as `Paid`, `Dues pending` or `Open`.

### Data directory

The console front end resolves `data/` against the current working directory,
which lands in a different place depending on how the binary was launched. The
desktop app resolves it explicitly: `ST_DATA_DIR`, then `./data`, then `../data`.

```text
ST_DATA_DIR=/path/to/data ./build/bin/transport_gui
```

## Design decisions

**Payments use two balances, not one.** The original stored a single `due` plus
a fixed registration fee and capped payments against `due` while the total
re-added the fee — so the full amount could never be paid. Now
`registrationFee` and `transportFee` are separate, a payment targets one bucket
and is capped at that bucket's remaining balance, and staff reports read the
same balances the student sees.

**Seat allocation lives in one service.** `SeatService` is the only writer of a
student's seat, which is what guarantees "one seat, one student". Changing route
releases the old seat and rolls back if the new one cannot be taken.

**Users are held polymorphically.** `std::vector<std::unique_ptr<User>>` — a
`vector<User>` would slice `Student`/`Staff` back to `User` and make every
downcast undefined.

**Staff registration needs a real secret.** The authorization code lives in
`data/config.csv` and is compared in constant time, rather than accepting any
non-empty string. It is a shared secret, not identity management — the
limitation is documented rather than papered over.

**Password hashing is honest about its limits.** It is a salted, iterated digest
behind `utils/Security.hpp`, with constant-time comparison. It is not a
production KDF; swapping in Argon2 or bcrypt touches one file.

**Storage is replaceable.** Everything above the repository layer is unaware
that CSV is used. Moving to SQLite means reimplementing five classes.

**Passwords cannot be recovered.** Because only digests are stored, the
forgot-password link explains this and points at the transport office rather
than pretending to offer a reset the system cannot perform.

## Editor setup (VS Code)

The workspace ships `.vscode/` configuration so IntelliSense resolves the
project's headers without guessing:

- `includePath` points at `include/` and `tests/` explicitly. A recursive
  `${workspaceFolder}/**` does not reliably resolve quoted project includes like
  `"models/User.hpp"` and drags the whole `build/` tree into the index.

- `cppStandard` is `c++17` (required for `std::filesystem`, `if constexpr`,
  `make_unique`).

- `compile_commands.json` is exported by CMake and consumed directly, so the
  editor sees the exact flags the project builds with.

- Tasks wrap CMake: **CMake: Configure / Build / Test**, plus **Run desktop
  GUI**. Launch configurations cover `transport_system`, `transport_gui` and
  every test suite.

> **Disable the "C/C++ Runner" extension** (`ms-vscode-2019.crunner`). It is
> built for the old single-file `g++ main.cpp` flow, it compiles one file at a
> time (which cannot link this project), and it keeps re-inserting its own
> `C/C++ Runner: Debug Session` entry into `.vscode/launch.json`. Its settings
> have been removed; reload the window once (`Ctrl+Shift+P` →
> *Developer: Reload Window*) to let the change take effect.
